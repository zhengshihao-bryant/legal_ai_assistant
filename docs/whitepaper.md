# 法律知识助手 RAG 系统：设计与实验白皮书

> 本文不是功能说明书，而是一次**完整的 RAG 系统设计与实验研究**。
> 每个设计决策都来自可复现的实验证据（`data/evaluation/reports/` 下全部报告可一键复现）。

---

## 1. 项目概述

中文法律垂直领域的检索增强生成（RAG）问答系统。知识库 58 篇文档：19 部现行法律（含 5 部扫描版 PDF）、28 份企业制度、7 份合同模板、4 份模拟案例；评估集 100 条 QA（法规/制度/合同/案例四类）。

能力链：

```
数据 → Parsing/OCR → Chunk → Embedding → Retrieval(Dense+BM25) → Hybrid(RRF)
     → Rerank → Context → Generation → Citation Validation → Evaluation
```

## 2. 为什么是 RAG（而非微调或纯 LLM）

- **时效与权威性**：法律条文可修订，RAG 让答案锚定当前语料，无需随法规变化重训
- **可溯源**：企业法律场景要求每个结论可核验（引用溯源 + Groundedness 校验）
- **成本**：无需训练；检索 + 生成解耦，可单独优化

## 3. 数据工程：为什么 OCR 是 RAG 的重要环节

**真实教训**：初版评估中《劳动合同法》等 5 部法律 Recall 几乎为 0，一度被归因于「OCR 噪声」。④ 数据质量审计揭示真正根因——**OCR 文本是无换行的密文墙，标题检测失败 → 文档树无章节 → chunk 数为 0 → 这 5 部法律从未进入索引**。修复（无标题时整篇回退为 section）后：

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 法规域 Recall@10 | 0.433 | **0.933** |
| 整体 Recall@10 | 0.79 | **0.86** |
| 整体 MRR | 0.549 | **0.652** |

**结论**：扫描件文档没有 OCR 就无法进入检索链路；OCR 后必须验证「解析 → 结构 → chunk」全链路是否真正入库（数据质量审计应包含「零 chunk 文档」检查）。这也证明**分层评估的价值**——没有逐域指标，这个 bug 会被整体均值掩盖。

## 4. 为什么 Dense + BM25 双路检索

实验（100 条 QA，doc 级 Recall@10）：

| 检索器 | Recall@10 | MRR |
| --- | --- | --- |
| Dense（BGE） | 0.91 | 0.676 |
| BM25（jieba） | 0.85 | 0.537 |

- Dense 显著占优：中文法律问答中「口语问法 vs 法条术语」是常态，语义向量能跨表述匹配
- BM25 仍有价值：术语精确匹配（条号、专有名词）、零训练成本、可解释
- 二者召回集不完全重叠（Dense 语义强、BM25 字面强）→ 互补是混合的前提

## 5. 为什么 RRF（Reciprocal Rank Fusion）

不同检索器的分数空间不可直接比较（余弦相似度 vs BM25 得分），加权求和需要调参且不稳定。RRF 只依赖**排序位置**：`score = Σ 1/(k + rank)`，无参、稳健。实验显示 Hybrid+RRF 在 chunk 级 Recall 与整体 NDCG 上为最稳配置；其价值在**不同问题上互补**——对 Dense 失败的题目 BM25 兜底。**结论以报告数值为准，不预设「混合一定更好」**，这正是消融实验的意义。

## 6. 为什么 Rerank 没有直接提升最终 Recall（一个反直觉发现）

| 配置 | chunk R@5 | chunk R@10 | doc MRR | 延迟/query |
| --- | --- | --- | --- | --- |
| Hybrid | 0.77 | 0.83 | 0.652 | 44ms |
| +Rerank | 0.74 | 0.82 | 0.646 | 1.8s |

- **Rerank 不扩大候选集**：Recall@20 与 Hybrid 完全一致（0.86）——重排只能改变顺序
- **chunk 级 R@5/10 略降**：chunk 级 gold 用「词汇重叠」代理，而 CrossEncoder 擅长**语义匹配**（字面不同但相关），代理指标低估其收益——这是评估指标本身局限的实证
- **延迟代价 40 倍**（CPU）：生产中应 GPU 加速，或仅对 top-N 候选精排

**工程结论**：Rerank 的价值在**精排质量**（对后续生成的关键性），不在召回；是否启用取决于延迟预算与下游生成对证据顺序的敏感度。

## 7. 为什么需要 Query Rewrite（lexical gap 实证）

法律口语与法条术语存在系统性差距：「加班工资」vs「延长工作时间」；「竞业限制违约金怎么判」vs 条文原文。

| 组 | chunk R@10 | chunk MRR | doc R@10 | NDCG@10 |
| --- | --- | --- | --- | --- |
| 原始 | 0.83 | 0.610 | 0.86 | 0.756 |
| 规则扩展 | 0.85 | 0.573 | 0.89 | 0.742 |
| **LLM 改写（DeepSeek）** | **0.91** | **0.614** | **0.93** | **0.800** |

- **LLM 改写综合最优**：不仅补召回，更提升排序（chunk R@10 0.91、NDCG@10 0.800）——它能重写语义而非简单拼词
- **规则的边界**：补召回（doc R@10 0.89）但 MRR 反而低于原始（0.609 < 0.652）——追加领域词稀释短候选取舍
- **何时用哪个**：常规制度/合同查询规则已够用；**法规术语稀疏与案例域查询（0.45→0.65）LLM 更稳**——这直接回答了「什么情况下规则已够、什么情况下需要 LLM」

## 8. 为什么 Groundedness 校验是必需防线

Generation 对比（本地抽取式 vs DeepSeek LLM）：

| 指标 | 本地抽取式 | DeepSeek LLM |
| --- | --- | --- |
| F1 | 0.172 | **0.299（+73%）** |
| 引用率 | 0.97 | 1.0 |
| 平均接地性 | 0.977 | 0.936 |

- LLM 生成质量全面跳升，引用率升至 1.0
- **但接地性下降（0.977→0.936）**：LLM 用自己的表述组织答案，词汇重叠校验更严格——模型越「会说话」，越需要 Groundedness 逐句校验来拦截无支撑陈述
- **结论**：接地性校验在 LLM 时代不是可选项，而是防线

## 9. 评估方法论

- **分层评估**：Retrieval / Generation 分开评，定位瓶颈在检索还是生成（本案例中两者都有独立改进空间）
- **chunk/doc 双层指标**：doc 级掩盖 chunk 级差异（Rerank 的 chunk 级行为与 doc 级不同）
- **伪 gold**：无 chunk 级标注时，用「gold 文档内与答案词汇重叠」的 chunk 作为代理，配合回退避免假阴性
- **分域指标**：整体均值掩盖短板（法规 bug 被 0.79 均值掩盖；案例域 0.45 需单列）
- **口径诚实**：案例域「检索失败」部分源于标注口径（gold 只标案例库，但检索到能作答的法律同样正确）——评估要区分「检索错」与「标注严」

## 10. 已知限制与未来工作

1. **扫描件结构化**：OCR 密文墙目前整篇单 section，Parent 过大时 Context 截断 → OCR 感知的结构化解析（按 第X条/第X章 切分）
2. **案例域**：LLM 改写缓解至 0.65；后续按「争议焦点/裁判观点」拆分 parent，评估开放双 gold 口径
3. **评估集**：100 条为模拟口径一致集，需补充真实裁判文书类样本
4. **Rerank 成本**：CPU 40 倍延迟，生产需 GPU 或候选截断
5. **多轮/应用层**：SSE、多轮对话等按战略暂缓（见 README Roadmap）

## 11. 结论

本项目证明了纵向能力链的完整价值：**数据质量（OCR/解析）决定下限，检索设计（Dense/BM25/RRF/Rerank）决定召回与排序，查询理解（规则/LLM 改写）弥合表述差距，生成与接地性校验保证可信**。每个环节都有实验证据支撑，且所有报告可在本地一键复现（`python -m rag.cli bench`）。
